# Phase 4: Solo Practice

**Goal:** The Agent plays full solo Ironclad runs through the mod, reviews every run, improves the playbook based on evidence, and climbs the ascension ladder. Target: milestones M1–M3, ideally M5.

**Depends on:** Phase 0 and Phase 2. Phase 3 is strongly recommended.
**Unblocks:** Phase 5 and Phase 6.

---

## 1. What to expect

| | |
|---|---|
| **Run length** | About 400–500 actions per full run. At a few seconds per action, plus thinking time on big decisions, expect 1.5–3 hours of wall time per run. |
| **Player involvement** | Not required during a run. The Player starts the session, may watch or chat, and gets a notification when the run ends. Reviewing post-mortems is optional. |
| **Early results** | The first runs will probably die in Act 1 or Act 2: interface mistakes, arithmetic slips, over-greedy pathing. That is expected. The aim of the first 3 runs is M1 (a clean run with no interface failures), not wins. |
| **Learning curve** | Improvement comes from playbook changes after each run. Expect it to come in steps: a cluster of fixes, then a plateau. |
| **Cost** | Tokens per run are recorded. A public reference: the STS2MCP author reports about 8M tokens per full Ironclad run for a smaller model. A larger model that reasons more per decision may use more. |
| **What can go wrong** | Mod errors mid-run, context compaction during long runs, the Mac sleeping, permission prompts while the Player is away. Each has a mitigation below. |

## 2. Run folder layout

```
runs/<YYYY-MM-DD>-<seed>/
  journal.md        live plan, updated every floor (template: templates/run-journal.md)
  decisions.jsonl   export of GET /decisions at run end (every action with its reason)
  run.run           copy of the game's run history file
  facts.md          generated by tools/postmortem.py
  postmortem.md     written analysis (template: templates/postmortem.md)
```

### Run journal template (`templates/run-journal.md`)

```
# Run <date> <seed>: Ironclad A<n>, playbook v<x>
## Status: floor <f>, act <a>, HP <hp>/<max>, gold <g>
## Deck plan: archetype target, what the deck needs next (damage / block / draw / scaling / AoE)
## Act path plan: chosen path, HP budget per node, re-plan triggers
## Upcoming threats: likely elites / boss and their checklists
## Floor log: one line per floor (room, result, HP change, notable decision)
## Open concerns
```

## 3. Epics and stories

### P4.E1: Run harness

> **P4.E1.S1: Run start procedure** · Size S · Status: Done (docs/runbooks/start-run.md)
> *As the Agent, I want a fixed start routine, so that every run is set up and logged the same way.*
>
> **Acceptance criteria**
> - [ ] `docs/runbooks/start-run.md` lists the steps:
>   1. Confirm `/health`.
>   2. Request keep-awake.
>   3. Choose the character, ascension and seed from the ladder (E6) or an exam seed (E5.S2).
>   4. Create the run folder from the templates.
>   5. Write the journal header with the playbook version.
>   6. Start the run through the API.
> - [ ] The Player gets one chat line: "Starting run: Ironclad A<n>, seed <s>, playbook v<x>".

> **P4.E1.S2: Decision loop** · Size M · Status: Done (docs/runbooks/decision-loop.md)
> *As the Agent, I want one documented loop for every decision, so that play is consistent and auditable.*
>
> **Acceptance criteria:** `docs/runbooks/decision-loop.md` specifies:
> 1. Read the brief state (`tools/sts.py state --brief` or the MCP `decide`).
> 2. Classify the screen and resolve any overlay first.
> 3. Load only the playbook section the screen needs.
> 4. Decide. Big decisions (rare cards, relics, elite paths, boss turns) get explicit reasoning. Routine ones stay short.
> 5. Act, with `client_context.decision_reason` set to one sentence.
> 6. Verify that the state advanced as expected. If not, follow E1.S4.
> 7. On each new floor, update the journal.
> - [ ] Only actions in `available_actions` are used. Indexes always come from the latest state, never from memory.

> **P4.E1.S3: Screen handlers** · Size M · Status: Done (screen handlers in decision-loop.md)
> *As the Agent, I want a short procedure per screen type, so that no screen is handled by improvisation.*
>
> **Acceptance criteria**
> - [ ] The decision loop runbook has one subsection each for: map, combat, card reward, relic and potion reward, shop (open, buy or remove, close, proceed), rest site, event, treasure, Ancient, card selection overlays (upgrade, remove, transform), boss relic, and game over (`continue_game_over` before anything else).

> **P4.E1.S4: Error recovery** · Size S · Status: Done (error table in decision-loop.md)
> *As the Agent, I want a table of errors and responses, so that a mod error does not end a run.*
>
> **Acceptance criteria:** the runbook has this table, extended with what Phase 0 observed.
>
> | Error or symptom | Response |
> |---|---|
> | `invalid_action`, `invalid_target`, `invalid_request` | Fix the call from `error.details`; re-read the state; do not retry blindly |
> | `409 action_in_flight` | Wait briefly, then retry once |
> | `outcome_unknown` | Never replay; re-read the state and decide again |
> | `combat.action_readiness` false | Wait for transient reasons (`hand_in_card_play` and similar); do not spam reads |
> | The screen does not change after an action | `wait_until_actionable`, then re-read; check for overlays or modals |
> | `/health` unreachable | Tell the Player; once the game is relaunched, `continue_run`; resume from the journal |

> **P4.E1.S5: Resume after compaction or restart** · Size S · Status: Todo
> *As the Next Session, I want to resume a run mid-way with no memory of it, so that long runs survive context compaction and crashes.*
>
> **Acceptance criteria**
> - [ ] The project instructions say: if `runs/` has a journal without a post-mortem, read that journal and `/state` before doing anything else.
> - [ ] The journal holds enough to continue the plan: the deck plan, the path plan and the threats.
> - [ ] Tested once on purpose: start a new session mid-run and continue correctly.

> **P4.E1.S6: Run end procedure** · Size S · Status: Done (docs/runbooks/end-run.md)
> *As the Agent, I want each run closed out the same way, so that post-mortems always have complete data.*
>
> **Acceptance criteria**
> - [ ] `continue_game_over`.
> - [ ] Copy the new `.run` file into the run folder.
> - [ ] Export `GET /decisions` to `decisions.jsonl`.
> - [ ] Append a scoreboard row.
> - [ ] Notify the Player (a push notification, if they are away).

### P4.E2: Combat procedure

> **P4.E2.S1: Turn-planning checklist** · Size S · Status: Done (playbook section 9, steps 1–10; tools/plan_turn.py searches the turn; 2026-11-19; card-specific rules, playable statuses, 17 potions and the boss and elite powers added overnight)
> *As the Agent, I want a fixed checklist for each combat turn, so that I do not skip a step under pressure.*
>
> **Acceptance criteria:** the checklist in `playbooks/ironclad.md` (combat section):
> 1. Read every enemy intent. Total the incoming damage after Weak and the player's block modifiers.
> 2. Lethal check on enemies: can this turn kill one, or all? Killing removes its damage.
> 3. Block needed = incoming − acceptable HP loss. Acceptable HP loss comes from the act's HP budget.
> 4. Draw and energy cards first when they change the options. Powers early in the fight. Apply Vulnerable before attacks. Apply Weak before the enemy attacks.
> 5. Potions: use one if it prevents a significant loss of HP or wins a dangerous fight. Never hold three potions into a boss.
> 6. Check `end_turn_will_kill_player` and `lethal_risks` before ending the turn.
> 7. Record the expected HP after the enemy acts. Compare it with the actual HP next turn, to catch arithmetic mistakes.

> **P4.E2.S2: Damage and block calculator** · Size M · Status: Done (tools/calc.py, 18 tests; rules unverified until in-game checks)
> *As the Agent, I want a calculator for damage and block with every modifier, so that arithmetic errors do not cost HP.*
>
> **Acceptance criteria**
> - [ ] `tools/calc.py` handles Strength, Vulnerable, Weak, Frail, Dexterity, multi-hit attacks, block on the target and the order of operations, using `knowledge/mechanics.md`.
> - [ ] It is verified against at least 10 in-game numbers from the Phase 2 verification list. Unit tests live in `tools/tests/`.

> **P4.E2.S3: Multi-enemy targeting rules** · Size S · Status: Done (playbook section 9 step 10; plan_turn.py target search with Minion and Crab Rage rules; untested live)
> *As the Agent, I want rules for choosing targets, so that damage goes where it reduces incoming damage most.*
>
> **Acceptance criteria**
> - [ ] Rules are in the playbook: kill priorities (highest damage per HP remaining, summoners, buffers), AoE thresholds, and overkill avoidance. Encounter-specific overrides link to the enemy notes.

> **P4.E2.S4: Fight logging** · Size XS · Status: Done (tools/journal.py fight: encounter, turns, damage, band benchmark, potions)
> *As the Agent, I want each fight summarised in the journal, so that the post-mortem can compare it with the benchmark.*
>
> **Acceptance criteria**
> - [ ] One line per fight: encounter, turns, damage taken, the benchmark median for that encounter, potions used.

### P4.E3: Strategy procedures

> **P4.E3.S1: Plan the path at the start of each act** · Size M · Status: Done (tools/path.py ranks every route; start-run runbook step 7; practice in the first runs)
> *As the Agent, I want to plan the whole act's path at its start, so that elites, rests and shops are sequenced against an HP budget.*
>
> **Acceptance criteria**
> - [ ] At each act start: list candidate paths, score each (elites, rests before elites and the boss, shops, unknowns, expected HP cost from the benchmark), choose one, and write it in the journal.
> - [ ] Re-plan triggers: HP below budget by more than 15% of max, a key card or relic gained, or a forced detour.

> **P4.E3.S2: Card reward procedure** · Size S · Status: Done (tools/draft.py implements the steps and prints the reasons)
> *As the Agent, I want a fixed way to evaluate card rewards, so that picks follow the deck's needs rather than card strength alone.*
>
> **Acceptance criteria**
> - [ ] Steps:
>   1. Assess the deck's needs against the checklist (front-loaded damage, block, draw, scaling, AoE) for the next elite and boss.
>   2. Look up the tier and context rules in the playbook.
>   3. Check archetype fit.
>   4. Apply the skip rule: skip if no option improves the deck for the coming fights.
> - [ ] The reason recorded names the need the pick addresses.

> **P4.E3.S3: Rest, shop, event, Ancient and relic procedures** · Size S · Status: Done (tools/advise.py handlers cite playbook sections; Ancient and relic choices still by hand)
> *As the Agent, I want each non-combat choice tied to a playbook section, so that these decisions are as disciplined as card picks.*
>
> **Acceptance criteria**
> - [ ] Each screen handler in E1.S3 cites the playbook section it uses.

> **P4.E3.S4: Deck check at the end of each act** · Size S · Status: Done (tools/deck_check.py: corner targets and countable boss checklist items)
> *As the Agent, I want to check the deck against the next act's demands, so that problems are caught while there is still time to fix them.*
>
> **Acceptance criteria**
> - [ ] Before each boss and at each act start: compare the deck with the boss plan checklist (Phase 2 E5). Record the gaps and the plan to close them in the journal.

### P4.E4: Post-mortem

> **P4.E4.S1: Facts sheet** · Size M · Status: Done (tools/postmortem.py; tested on three of the Player's runs)
> *As the Agent, I want each run's facts generated automatically, so that the post-mortem starts from numbers, not memory.*
>
> **Acceptance criteria**
> - [ ] `tools/postmortem.py <run folder>` writes `facts.md`, with:
>   - the HP curve
>   - per-fight damage against the benchmark median (flagging fights above the p75)
>   - decision counts by screen
>   - errors
>   - potions used, wasted and held at death
>   - the deck and relics at death or victory

> **P4.E4.S2: Mistake analysis** · Size S · Status: Todo
> *As the Agent, I want to identify the costliest decisions, so that each run teaches something specific.*
>
> **Acceptance criteria:** `postmortem.md` lists the top 3 decisions by estimated cost, each with:
> - [ ] What was decided and why (from `decisions.jsonl`).
> - [ ] What should have happened instead.
> - [ ] The evidence.
> - [ ] Whether the playbook would have prevented it. If not, a proposed rule.

> **P4.E4.S3: Playbook change control** · Size S · Status: Todo
> *As the Player, I want playbook changes to be deliberate, so that one unlucky run does not rewrite the strategy.*
>
> **Acceptance criteria**
> - [ ] At most 5 changes per run.
> - [ ] Each change states its evidence, the expected effect and its label.
> - [ ] A change based on one run is labelled `[HYPOTHESIS]` until it is seen again.
> - [ ] The version is bumped (v4, v5, …), with a changelog entry and a git commit.

> **P4.E4.S4: Optional Player review** · Size XS · Status: Todo
> *As the Player, I want a short summary of each run, so that I can follow along without reading files.*
>
> **Acceptance criteria**
> - [ ] A 5-line summary in chat: result, floor, cause of death, biggest mistake, playbook change.
